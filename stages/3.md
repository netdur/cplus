# Stage 3 — the platform-free body

Status: **built, 2026-08-04 — under review.** Everything below is
implemented per this page: the tier symbols (six modules), the mount seam
with M1-M7 answered (mount.cplus), the renames (Job/run_job/run_on_worker,
Chrome `bar: Bar`, set_content), switch_to over Display::None, the 12
deferred rows emitted as fn+ctx pairs (the events dependency died with
decision 5's caveat — Subscription is bus-coupled), FontWeight + is_italic,
guard 5, the key band (`.gesture(on_key:)` + readers), and
`find(key, within:)` over `mounted_root()`. facet suite 430, plain/asan/
release. This page was rewritten 2026-08-03 to match what Stage 2 left
behind; the previous version was a stub.

## What Stage 2 already did, so this stage does not

The stub asked for: `Color`/`Size`/`Rect`/`Point`, `Style`, `Node` + modifiers,
the Builder, leaves, containers, `Handle` + `find`. All of that exists, and two
of them exist differently enough that the old wording would mislead:

- **`Handle` is gone.** `find` is per-control and returns
  `Option[<Control>]`. Do not port a generic handle back; the whole point is
  that a wrong verb is E0324 and a wrong kind is `None`.
- **`Style` is flex's**, not facet's, and `Node` is flex's `Node`. facet holds
  zero layout code and should keep holding zero.

What remains is everything between *a description* and *a running application*.

## The one thing everything else waits on

**The mount seam.** facet has a tree, 42 controls and a dirty word per node,
and nothing reads any of it. Until something walks the tree and hands it to a
backend, nothing facet declares can appear on a screen.

Three parts, all platform-free — the walk is the same everywhere, only what it
calls into differs:

1. **`Renderer`** — the vtable a backend fills. Create a view for a kind,
   apply a node's dirty bits, insert and remove children, destroy a view. The
   count that keeps coming up is ~37 apply functions, one per control, plus the
   shared band.
2. **The mount walk** — descend a tree, create views, attach, set
   `is_attached`, fire `on_attach`.
3. **The sync walk** — find nodes with a non-zero `dirty`, apply, clear.
   `begin_updates` / `end_updates` already coalesce; `C_FLUSH` is the bit that
   says a batch closed.

Design constraint already fixed by Stage 2: a setter writes one field and sets
one bit, and a command is the same shape. So the seam is a per-kind apply
function reading bits, never a verb-indexed table of registrars.

### What the seam forces you to decide

Seven, and the first is a hole in what Stage 2 shipped.

**M1. Who releases the native view.** `Data` frees `props` through a stored
`release`, and `gestures` through a stored `gestures_release`. `view` has
NOTHING. Mount a node, drop it, and the view leaks — or worse, survives in a
superview with nothing owning the facet side. The answer that matches the two
precedents already in the struct is a third pair:

```
opaque view: *u8,
view_release: fn(*u8),      // the backend sets both when it mounts
```

Do this before writing a backend, not after. It is four lines now.

**M2. Where the Renderer lives.** One backend per process is the truth, so a
single `Renderer` value set at startup is honest. Note this is NOT what Stage 2
rejected: the objection was to 338 per-verb fn-pointer statics, not to one
vtable of ~40 hooks. Still a decision — a static, or a value threaded through
`mount`.

**M3. Creation order.** Top-down (parent, then children) or bottom-up
(children, then parent)? It decides whether a parent can size itself to
children as it mounts, and AppKit and GTK do not agree on what is natural.

**M4. `present` inside `on_attach` re-enters the walk.** iris does exactly
this:

```
fn on_attach(ref this) {
    facet::find("welcome:main").present(this.launcher);
}
```

So `on_attach` fires while the walk is still running, and presenting a child
starts a NESTED mount. Either the walk is re-entrant, or `present` queues and
the walk drains a work list before finishing. Pick one deliberately; finding
out by recursion is not a plan.

**M5. What schedules a sync.** `C_FLUSH` says a batch closed and
`begin_updates`/`end_updates` coalesce, but nothing runs the sync walk. A
display link every frame, an explicit `facet::sync()`, or a flush when the
batch depth returns to zero? This decides whether a setter is visible
immediately or at the next turn of the loop, which is an observable difference
an application will build on either way.

**M6. Thread discipline.** `Job::run` mutates a struct off-main and `on_ready`
fires on main. NOTHING stops a job from touching the tree off-main. A rule in a
comment, a debug assert, or a thread id on `Data` checked in `touch`? The first
is free and the last is the only one that catches it.

**M7. Which tree is "the mounted tree"** when a global `find("save")` has three
windows to choose from. Carried from the find decision below.

## Then, in this order

1. **Depend on `events`.** Small, and it unblocks 12 rows Stage 2 had to
   record as deferred: the 5 shared-band events (`on_focus` `on_blur`
   `on_attach` `on_detach` `observe_size`) and the 7 continuous control events
   (`observe_scrolled` ×4, `observe_drag_interaction`,
   `observe_move_hover_interaction`, `observe_swipe_changing`). Both lists are
   guarded in `tools/gen_contract.py`: move a row out of one and the run fails
   until it is emitted or recorded elsewhere.
2. **Lifecycle.** `on_attach` / `on_detach` fire from the mount walk.
   `Data.is_attached` and `facet::set_attached` are already there for it.
3. **Components.** `Component`, `build(ref this)`, `component_at`, `key_of`,
   `raise`. Static-free: handlers bind `this` and reach siblings through
   `find(#addr_of(this), key)`. Do not reintroduce a static registry.
4. **Background work — renamed on the way in.** `load_service` does not load a
   service: it runs `produce()` on a worker and calls back on main. Nothing is
   loaded and nothing is a service.

   | old | new |
   |---|---|
   | `interface Service` / `fn produce(ref this)` | `interface Job` / `fn run(ref this)` |
   | `load_service(this, on_ready, ctx:)` | `run_job(this, then: on_ready, ctx:)` |
   | `on_worker(f, ctx)` | `run_on_worker(f, ctx)` — pairs with `run_on_main`, which it did not |

   `Job` and not `Producer` on the evidence: two of iris's three uses produce
   data (an fs walk, a git status) but the third scaffolds a project — git
   init, files written, package manager invoked. That is an action, not a
   production, so `Producer` would be a lie on one in three.

   Not `facet::run(this, then:)` either, short as it is: `run()` is what an
   application's main loop is called almost everywhere, and that collision
   costs more than the repeated word. 26 call sites in iris, all mechanical.
5. **Scheduling.** `run_on_main`, `on_worker`, `after` -> `Cancellable`.
   Async-for-UI was tried and rejected: `block_on` freezes the loop.
6. **Chrome — kept, with the booleans collapsed.**

   `Chrome` is the right word and stays. It means the shell around content,
   which is true on all six backends: macOS titlebar, GTK headerbar, Win32
   caption, iOS status and navigation bars, Android status and app bar.
   `Window` was considered and rejected — it is true on four of the six, and
   the one place facet must not name a platform is its own contract.

   Per-screen chrome also fits mobile BETTER than the platform it was written
   for: iOS pushes a nav bar per view controller and Android sets the app bar
   per screen, while a desktop window persists and only its title changes.

   What changes is the six booleans — `clean_titlebar`, `close_button_only`,
   `custom_chrome`, `native_buttons`, `unified_toolbar`, `hide_title`. That is
   64 combinations for one decision, and `custom_chrome` inside `struct Chrome`
   is the name eating itself. iris gives the game away by setting two of them
   together, because they were never independent:

   ```
   clean_titlebar: true, close_button_only: true
   ```

   One enum, named for the shell rather than for a titlebar:

   ```
   bar: Bar
   enum Bar { Native, Blended, Hidden, Custom }
   ```

   `Blended` covers macOS's unified toolbar and `clean_titlebar` without naming
   either. `Custom` now means something concrete — the application draws it
   with `window_buttons()` and `.window_drag()`, both shipped in Stage 2.
   Which buttons appear is a separate question from the bar's style, so
   `close_button_only` separates out rather than folding in.

   **The struct stays FLAT.** An earlier draft grouped size and zoom as hints
   "only a resizable host honours". That grouping was wrong twice over: a
   MacBook Pro has a notch, so `SafeArea` is not a phone thing; and iPadOS has
   windows, so sizing is not a desktop thing. Any capability-shaped grouping
   ages out within an OS release. facet offers every field and a backend
   honours what it can, recording the rest in its own manifest — which is the
   invariant this package already runs on, not a new rule.

7. **Screens and navigation.**

   **`Screen` is `Component` + `Lifecycle` + two methods** — `chrome()` and
   `menu_items()`. `ScreenBox` is hand-rolled `dyn`: an instance pointer plus
   six trampolines, so an application can hold screens of different types in
   one registry. Both are the no-`dyn` tax, not a design.

   The analogy is Activity and Fragment, with one difference to PROTECT:
   Android's are separate base classes with separate lifecycles, and every
   complaint about them traces to two lifecycles that do not nest. facet has
   ONE — `on_attach`/`on_detach`, identical at both levels. Keep it that way
   and the whole category never arrives.

   Part of `Screen`'s weight is the language's: C+ interfaces carry no default
   bodies, so a screen with nothing to add still writes
   `fn menu_items(this) -> Vec { return vec::new(); }`. If C+ ever gains
   defaults, `Screen` collapses to one method.

   **Three verbs at three levels, and they were being confused for each other:**

   | verb | scope | on repeat |
   |---|---|---|
   | `set_content(component)` | fill one slot | rebuilds |
   | `switch_to(component)` | siblings in an outlet — tabs, panes | parks and restores |
   | `nav::go` / `push` / `pop` / `quit` | whole screens, by route name | desktop opens/closes windows; mobile drives the nav stack |

   **`present` is renamed `set_content`.** In UIKit `present` means exactly one
   thing — `presentViewController:`, MODAL presentation — and facet's does the
   opposite: it is containment, what UIKit calls `addChild` + `addSubview`. The
   verb that IS modal-ish here is `nav::push`, one module over. A false friend
   of exactly the kind the naming lint exists to catch. `set_content` is also
   what facet already calls a slot's contents (`bordered`, `scroll`), so the
   word is not new — reconcile the Node-taking and Component-taking forms when
   porting.

   Whatever it is called, keep the four things it does, because each is
   load-bearing: build the component, make it the slot's ONLY child, force it
   to fill (`.grow(1).shrink(1)`, without which a component's plain-column root
   content-sizes and swallows the grow), register a detach trampoline, and fire
   `on_attach`.

   **`switch_to` becomes five lines over `Display::None`.** The old router is a
   static `ROUTER_STAGED` registry plus `Staged` and three trampolines, parking
   a screen by removing it from the tree and re-inserting it later. flex
   already does this with one style field, and it is strictly better —
   `remove_child` bumps `removal_count()` and invalidates EVERY cursor in the
   application, and on a backend `removeFromSuperview` throws away the scroll
   position, selection and first responder that parking was meant to preserve.
   Verified in `parking_keeps_cursors_live_and_state_intact`: a text field
   parked and unparked still reads what was typed into it, and a cursor held
   across the park stays live.

   The mechanism is flex's, the verb stays facet's: addressing is by key
   (`Data.key`) and the lifecycle hooks fire on the swap.

   **The nav module already ports.** Its own header says the verbs record
   intent — "no diffing, no hidden re-render" — and that the same
   `go`/`push`/`pop` drive a nav stack on a mobile backend. It was written
   portably before this conversation started.
8. **Theme.** `Theme`, `set_theme`, `is_dark`, two-tier tokens, live repaint.
   Port it knowing it did not land the first time: iris reads colour 149 times
   and only 8 of those go through a token. 94 are `Color::rgba` and 38 are
   `Color::adaptive` — so iris handles dark mode by supplying both colours at
   each site, which means a theme change cannot reach 141 of 149 places.
   Before porting, measure which colours iris repeats; that is the list of
   tokens it actually wants.
9. **The agent surface.** `agent.cplus`. The rule that already cost one revert:
   an agent has no hands, so a function the UI offers only as a gesture gets an
   alternative path in the UI, never a new verb on the agent surface.

`runtime_macos.cplus` / `runtime_linux.cplus` do **not** come back. facet names
no backend; `runtime.cplus` is the neutral facade only.

## The ledger debt this stage clears

82 ADOPT rows reach no control because they belong to a tier that does not
exist yet:

```
30  Window        14  Page       14  Toolbar
13  Application    8  TitleBar    3  ContentPage
```

The ledger already annotates the Window rows with their owner —
`set_root` is on Screen, the write rows are Chrome's, the reads and the
observe rows are the runtime's. Stage 3 is where those get homes.

**Add the fifth guard while doing it.** Stage 2's row guard only walks rows
that reach a control; nothing asks whether an ADOPT row reaches *anything*.
That is how 21 gesture rows sat unclaimed until an audit found them. The guard
belongs here because this stage is the first point at which every row has a
plausible owner: every ADOPT row reaches a control, a tier, or a recorded
exception, or the run fails.

## The global find — decided, waiting on the runtime

An agent over MCP holds a key and nothing else, so `find` cannot require a root
the caller does not have. One verb, one defaulted parameter:

```
button::find("save")                    // the mounted tree
button::find("save", within: panel)     // that subtree
```

`within:` and not `in:` because **`in` is a C+ keyword** — `find(key, in: p)`
is E0100 at the parameter, not a style preference. `within` also stays true
when the target is six levels down, which `parent:` does not.

Blocked only on the runtime knowing what is mounted, which is the first thing
this stage builds. One question it leaves open: with three windows open, "the
mounted tree" is ambiguous. Decide when the runtime lands.

## The two kinds of key — settled, do not re-litigate

One word was doing two jobs, and they have different lifetimes:

| | what it is | computed? | type | example |
|---|---|---|---|---|
| **`key`** | an ADDRESS — what `find` resolves | sometimes | `text::Text` | `button("Save", key: "save")` |
| **`id`** | an IDENTITY — which row is which across insert, remove, reorder | ALWAYS | `text::Text` | `TreeNode::new("Docs", "/docs")` |

They look swapped to anyone coming from the web, where `id` addresses and
`key` identifies a list row. The web is the outlier — SwiftUI has
`Identifiable.id`, UIKit has `ItemIdentifier`, RecyclerView has `getItemId`.
facet targets native, so identity is `id`.

`key` also earns its name three times over: a mounted node's key is what
`find` resolves, what the agent surface addresses, and what the backend sets as
the platform's accessibilityIdentifier. One token, three jobs.

**The forward rule:** when `list` and `collection` gain row identity, it is
`id`, matching `TreeNode.id`. Not `key`. That is the mistake this section
exists to prevent.

**And an `id` is derived from the ITEM, never from where the item sits.** A
path, a content hash, a record id — not `"row_0"` or `"row_${i}"`. A positional
identity renames every row after any insert, removal or sort, so selection,
expansion and view reuse follow the SLOT instead of the item. It reads as
"selection jumps to the wrong row", and it is the single most common way this
gets built wrong. Both halves are demonstrated in facet's suite:
`a_positional_identity_follows_the_slot_not_the_item` shows the selection
landing on the wrong person after one insert;
`a_content_identity_survives_the_same_edit` shows the same edit with a path as
the identity.

Encouraging it is a documentation job at the point of use, plus those two
tests. A type cannot tell a stable string from a positional one.

**On `str` versus `Text`, since the two kinds want different answers:**

- An **address** is few in number, repeats, and is usually a literal. `str` is
  natural at the call site and stays the constructor parameter type.
- An **identity** is always computed and churns with the data. It must be
  owned.

Interning would turn a computed string into a permanent `str`, which is exactly
"a key that cannot change". It is sound for addresses — few, repeated, bounded
— and wrong for identities, because a table that never evicts grows with every
row an application has ever shown. If interning is ever wanted, it is for
`Data.key` alone, and it stays an optimisation rather than a correctness fix.

`Data.slot` is a third string and is neither — it is a name a PARENT assigns to
a child so it can be replaced in place (`@header`, `@content`). It stays `str`
because only generated literals ever reach it.

## Found late, not yet decided

The iris audit of 2026-08-01 listed 23 tier symbols and 11 facet-origin words.
Re-running it against iris on 2026-08-03 turned up four more it never named.
Recorded here so they are not rediscovered a third time.

**1. There is no font weight, and it is the most-used missing thing.**

```
facet::weight_semibold  33
facet::weight_medium     6
facet::weight_bold       6
facet::weight_regular    1     -> 46 uses in iris
```

facet has `FontStyle`, which is MAUI's `FontAttributes` transcribed faithfully:

```
enum FontStyle { Bold, Italic, None }
```

Two things wrong with it, and both are MAUI's, inherited without question:

- **No scale.** Semibold and medium are unsayable. Every platform has a scale —
  `NSFont` runs ultraLight to black, CSS runs 100 to 900, and the icon font
  facet itself ships has a `wght` axis from 100 to 700.
- **Two axes in one enum.** Weight and slant are orthogonal, so "semibold
  italic" cannot be expressed at all.

The fix is a ledger change: `FontStyle` -> `FontWeight` (a scale) plus a
separate `is_italic`, touching the ~10 controls that carry a font. Bigger than
any of the eleven facet-origin words except `symbol`, and evidence-backed.

**2. `on_drop` fires but nothing reads the drop.** `gestures.cplus` declares
the drag-and-drop band and no accessor for the payload; iris has
`dropped_text` and `drag_targeted`. A drop handler that cannot read the drop is
not a drop handler. This one is a hole in what Stage 2 shipped, not a MAUI
inheritance.

**3. `present` is the composition verb and was never listed.** Six uses:
`facet::find("welcome:main").present(this.launcher)`. A component builds a
shell with keyed empty slots and fills each on attach; that IS how components
nest, and it is more load-bearing than several symbols that did make the list.

**4. There is no keyboard vocabulary.** `key_named`, `key_escape`. Small, but
`on_key` is recorded as existing in iris's components.txt, so something has to
carry a key.

## Decisions carried in — all settled 2026-08-03

1. **`Handle` stays gone.** 125 uses in iris; iris updates itself. The typed
   cursor is the model, and `facet::find_in` -> `*Node` -> `button::from(node)`
   covers the case where the kind is not known.
2. **Constructor-only for control props.** No chained build setters, so no ~300
   generated methods. The division that makes it read: control props say what
   the thing IS and go in the constructor, flex's chaining says where it GOES.

       label("Status", key: "st", text_color: c).width(120.0).padding(8.0)

3. **`key` storage: owned `Text`, DONE.** Not interning — that buys a
   pointer-compare `find` at the cost of a global table, hashing, thread safety
   and an eviction policy, none of which a correctness fix needs. The hole it
   closed is `bugs/str-field-outliving-its-text-is-not-caught.md`, since fixed
   in the compiler; owning is still right for a computed key either way.
4. **Gesture handlers decline, DONE.** `Handler = fn(*u8, *u8) -> bool`, where
   `false` passes the event to the next node up the backend's native parent
   chain. A control's own action keeps its void signature — a button's
   activation is the button's.
5. **`Cancellable` is `events::Subscription`.** One RAII handle, not two. Check
   first that `Subscription` carries no bus-specific baggage a timer does not
   want.
