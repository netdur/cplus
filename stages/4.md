# Stage 4 — facet_appkit: the contract on a Mac

Status: **planned 2026-08-04.** The previous stub here ("tests, standalone
— null renderer, headless suite") was absorbed by Stage 3: the fake
renderer/scheduler ARE the null backend, and the 433-test suite is the
headless gate every change already passes. This page replaces it with the
stage the project actually needs next.

INTENT.md is the judge: facet_appkit reads facet's contract and implements
it with AppKit — or states plainly that AppKit cannot. Nothing in the
backend that the contract did not ask for.

## What Stage 3 left ready

- **The install contract** (handoff records it): five structs + two slots.
  A backend fills `Renderer`, `Scheduler`, `KeyReader`, `SenderReaders`,
  `AgentHooks`, plus `theme::set_is_dark_fn` / `set_theme_changed_fn`.
  Zero fields keep the portable no-op. There is no other registrar; a hook
  family outside these is drift.
- **The conformance harness**: the fake renderer/scheduler tests exercise
  mount, sync, batching, lifecycle, set_content (including native removal
  via `Renderer.remove`), switch_to parking, and job settling. A backend
  that fills the same structs inherits a proven pipeline.
- **The ownership model**: process → Application (`app::current()`) →
  Window (plural) → node. `App::run` makes its record current; windows
  open/close through the application record.
- **The debt ledger**: guard 5b holds 58 tier rows deferred to THIS stage,
  each with a reason (window sizing/policy, density, modal stack, toolbar
  tier, TitleBar content, safe area, soft input). Each either lands here
  or its disposition becomes "AppKit cannot", recorded in the backend's
  manifest per INTENT.

Reference material (the copy-paste rule applies): the pre-regen macOS
facade `git show eb5b1b7:vendor/facet/src/runtime_macos.cplus` (748 lines —
window creation from Chrome, the App loop over nav intents, push/pop,
dialogs, focus observers), `vendor/appkit` (bindgen; hand additions go to
appkit_ext), `agent_appkit`, and the old `agent.cplus`
(`git show eb5b1b7:vendor/facet/src/agent.cplus`). `vendor/facet_appkit`
is an empty scaffold today; `vendor/facet_gtk` still speaks the OLD
per-kind renderer and is out of scope for this stage.

## Decisions — resolved with the user, 2026-08-04

1. **The sync tick uses AppKit's OWN loop**: a CFRunLoopObserver at
   before-waiting — the same flush point Core Animation commits on. No
   facet loop exists; the observer is the platform-native coalescer.
2. **The 58 rows: implement everything AppKit can do** during the sweep;
   the mobile-only handful (soft-input policy, nav-bar back button) are
   recorded "AppKit cannot (mobile concept)" in facet_appkit's manifest —
   the same INTENT doctrine as an UNSUPPORTED control verb. No third
   bucket.
3. **`find` is the DOM rule** (implemented in facet immediately): bare
   `find(key)` searches the running app's windows in OPEN order, first
   match wins — like getElementById; `within:` scopes a subtree or
   disambiguates a duplicated key across windows. `mounted_root()` stays
   for facades that want "the active window", but find no longer uses it.

## Inspection notes, 2026-08-04 — before any backend code

Read end to end first: `mount`, `services`, `component`, `gestures`, `theme`,
`application`, `screen`, `nav`, `facet`, `runtime`, `window_chrome`, plus
`vendor/facet_appkit.old` and the `eb5b1b7` facade. What follows is what that
turned up, split into what is settled, what is still open, and what a reader
should not have to re-derive.

### facet_appkit.old is wrong in KIND, not in detail

It targets a `Renderer` of ~34 per-kind op fields each returning a
`flex::Node` (two trees: a description tree mounted INTO a flex tree), a
`Handle` cursor API, ~60 loose `facet::set_*_fn` registrars, and a generated
`contract_appkit.cplus` of per-verb slots. None of that exists now: facet's
tree IS flex's tree, and the seam is five structs. Salvage is at the
AppKit-call level only — `ns_color` / `ns_font`, `shell_style_mask`,
`hide_window_button`, the menu builder and its validation IMP, pinch zoom,
the toolbar / titlebar installers, the window-lifecycle delegate,
`reposition` / `reposition_nested`. Everything around those is dead. Treat
the package as a snippet quarry, not a base.

### Settled during the inspection

1. **Geometry writes are now on the dirty path (DONE).** The size verbs —
   `set_width`, `set_height`, the percent pair, `set_grow`, `set_shrink`,
   `set_padding`, `set_margin`, `set_gap`, `set_justify`, `set_align`,
   `set_wrap`, `set_z_index`, `relayout` — wrote flex's style and set NO
   bit, so `sidebar.set_width(300.0)` in a click handler reached the tree
   and never the screen. They now touch a new shared-band bit
   `props::C_LAYOUT` (bit 62, added in `tools/gen_contract.py`, not by
   hand). The bit says GEOMETRY: the backend answers it with one layout
   pass per window and a frame walk, never with a re-read of that node's
   props. Two tests in `mount.cplus` cover it, including the batch case and
   the dataless/null negatives.

   **Why not poll instead.** The alternative was a layout pass every idle
   run-loop turn, with no facet change. Rejected because it would pay the
   cost forever instead of only when something moved — see the resize
   optimisation below, which the wake-on-write model is what preserves.

2. **`C_GESTURES` and `C_HANDLERS` were the same bit (DONE).** Both were
   `2^61`, so a backend could not tell "the gesture set was replaced" from
   "a focus/blur/attach/detach handler was swapped". `props.cplus` is
   generated, so the hand-written constant moved: `core::C_GESTURES` is now
   bit 63. A `2^63` u64 literal parses (probed). Covered by
   `a_gesture_change_is_not_a_handler_change` in `gestures.cplus`.

   Shared band after both changes: bits 48–57 state, 58–60 commands
   (focus / blur / flush), 61 handlers, 62 layout, 63 gestures. Bits 0–47
   remain the per-control space.

   Status: `cd vendor/facet && cpc test` = **436 green** (433 + 3).
   `--asan` / `--release` and the generator's byte-idempotency re-run were
   NOT re-run after these edits — do that before the first commit.

### The resize optimisation — found, and what survives

`9a54a0b perf(flex+facet_appkit): make retained relayout O(what-changed),
not O(tree)`, on top of `483a311`. Measured on iris during a live drag:

```
rebuild everything per frame     ~265 ms/frame   (~4 FPS)
retained relayout                ~30 ms horizontal, ~2 ms vertical
```

Three parts, and they must not be lost in the port:

- **Two update classes, not one.** `invalidate` (state changed → rebuild)
  versus `relayout` (geometry changed → reuse the tree you already have,
  re-run layout at the new size, `set_frame` the views that already exist).
  No render, no mount, no view churn.
- **flex's incremental cache actually gets hits.** It skips subtrees whose
  style / child count / grid signature / box are unchanged. Under the old
  rebuild path it never hit once, because every tree lived for exactly one
  `calculate_layout` call. Keeping the tree alive is what turned it on.
- **The frame walk prunes itself on the cache's verdict.** A cache-skipped
  child still gets its OWN `set_frame` (AppKit frames are parent-relative
  and the bottom-up Y flip reads the parent's height), but its DESCENDANTS
  are skipped — "thousands of no-op `set_frame` msgsends per frame on a
  large tree". Plus measure caches on the views as packed fixed-point
  associated ints.

**The flex half is intact**: `layout_changed()`, the `_cached_*` block,
`mark_content_changed`, `round_to_pixel` are all still in
`vendor/flex_layout`. Only the AppKit half (`reposition` /
`reposition_nested`) needs porting, and it ports nearly verbatim.

The old code re-laid out on exactly two triggers and never on a timer:
`windowDidResize`, and an app edit that changed the tree. Trigger one is
entirely inside the backend and ports as-is; trigger two is what `C_LAYOUT`
now carries.

### A SECOND contract gap, 2026-08-04 — `canvas` cannot be drawn on — CLOSED

facet declared no drawing vocabulary. `Drawable` was `fn(*u8, f64, f64)` — the
callback got its ctx and a size, and NOTHING TO DRAW WITH. MAUI's
`IDrawable.Draw` takes an `ICanvas`; facet's version dropped that parameter,
and `vocabulary.cplus` had no path, no fill, no stroke, no painter.

**Why it was missing, mechanically.** `tools/maui_spec.py` extracts from the
PublicAPI manifests, and Stage 1 downloaded TWO: `Microsoft.Maui.Controls`
and `Microsoft.Maui.Core`. `ICanvas`, `PathF`, `WindingMode`, `BlendMode`,
`TextFlow` and `VerticalAlignment` are in a THIRD assembly,
`Microsoft.Maui.Graphics`, whose manifest was never fetched. Nothing dropped
these rows — they were never in the room. The manifest is now on disk:

```
plans/facet/spec/maui_Graphics_PublicAPI.Shipped.txt
  src/Graphics/src/Graphics/PublicAPI/netstandard/PublicAPI.Shipped.txt
```

with `ICanvas.cs` / `PathF.cs` read alongside it, because the analyzer elides
the interface rows whose types are reference types (every `DrawString`,
`DrawPath`, `SetShadow`, `SetFillPaint`, `Font` and colour row).

**What was added, by hand.** `vocabulary.cplus`'s hand-written literal in
`tools/gen_contract.py` (the generator transcribes it verbatim; nothing was
re-derived from MAUI). `Winding`, `Blend`, `VerticalAlign`, `TextFlow`,
`PathOp`, `DrawOp`, `Transform`, `PathSegment`, `Path`, `DrawCommand`,
`Canvas`, plus `Point::of` / `Size::of` / `Rect::of` / `Rect::sized`, and
`Drawable` respelled `fn(*u8, *Canvas, Rect)` — IDrawable.Draw's own shape.

**The shape, and why.** A drawing is RECORDED, not called through. The
application appends commands to a `Canvas`; facet holds them; the backend
replays. That is the same three parts as a Node, a props struct and a
Renderer, and it buys three things:

- a redraw at a new size replays without asking the application again,
- a drawing is READABLE, so facet's own suite asserts one with no backend —
  the nine tests in `test_main.cplus` run headless,
- a backend writes ONE replay loop instead of forty registered callbacks, and
  no sixth install struct joins the seam.

What it costs is `ICanvas.GetStringSize`: measuring text needs a live platform
context and at record time there is none. Not adopted; recorded in the
backend's MANIFEST.

### A THIRD gap, same day — `redraw()` was dropped as ENGINE

`GraphicsView.Invalidate()` is how an application says its drawing changed,
and the ledger had no verb for it. The cause is in `maui_map.py`: the methods
band INVERTS — application verbs are whitelisted in `METHOD_VOCABULARY` and
everything else drops as ENGINE — and `Invalidate` was never whitelisted. It
reads like MAUI's `InvalidateMeasure` plumbing and is not.

Fixed by the whitelist row plus a `COMMANDS` entry that writes nothing: the
drawing is the Drawable's, so the command only has to raise the bit the
backend watches. `canvas::Canvas::redraw()`, `P_REDRAW`.

### A CONTRACT gap the backend found, 2026-08-04 — FIXED

Stage 4 went to implement `context_menu` and there was nothing to put in the
NSMenu: **`context_menu_item` carries only a shortcut.** No text, no icon, no
click handler. Same hole in `swipe_item` (only `on_invoked`) and
`toolbar_item` (only `placement` + `priority`).

The cause is in the generator, not the backend. In MAUI all three derive from
`MenuItem`:

```
MenuFlyoutItem : MenuItem
SwipeItem      : MenuItem
ToolbarItem    : MenuItem
```

The ledger lists each type's OWN declared members, so `Text`,
`IconImageSource`, `IsDestructive` and `Clicked` sit under the `MenuItem`
section and reached only the `menu_item` module. `EXTRA_BASES` in
`tools/gen_contract.py` is exactly the mechanism for this (it is how `Entry` /
`Editor` / `SearchBar` inherit `InputView`), and the three are missing from it.

**The one-line fix alone does not work, and this is why.** Adding

```python
"MenuFlyoutItem": ["MenuItem"], "SwipeItem": ["MenuItem"],
"ToolbarItem": ["MenuItem"],
```

regenerates cleanly and passes all six guards, and the derived modules gain
`set_text` / `set_icon` / `set_destructive` / `on_clicked` correctly. But it
makes `MenuItem` both a BASE and a CONTROL — every existing base (`InputView`,
`ItemsView`, …) is a base only, with no module of its own. `ALL_BASES` then
emits `MenuItemProps` as a base block AND the control pass emits it again:

```
props.cplus: error[E0301]: duplicate type definition `MenuItemProps`
```

**What the fix was.** The generator now knows a base may also be a control,
in the two places that distinction matters:

- `base_block(src, owner)` takes the type the row is being emitted FOR. A base
  that is also a control reaches its own fields directly (`this.text`), and is
  a block only from a DERIVED control's point of view (`this.menu_item.text`).
- `emit_props` skips the struct for a control that is itself a base —
  `emit_base_props` already emitted it, with exactly those fields — while
  still emitting the kind tag and the release fn, which belong to the control.

So `MenuItemProps` is declared once. `menu_item` addresses it directly; the
three derived controls embed it as `menu_item: MenuItemProps`. Both paths are
exercised by
`the_menu_item_band_reaches_every_control_maui_derives_from_it`.

One breaking change falls out, and it is the right one: `context_menu_item`
and `toolbar_item` now take `text` as their leading argument, the way
`menu_item` always has. An item without a title was never usable.

Stage 2 work surfaced by Stage 4 — which is what building a backend against a
contract is for.

### What item 4 found, 2026-08-04

Four, all fixed:

1. **A gesture node with no key was never backed.** `wants_view` answered
   false for a bare `K_NODE` without a key, so `column(b).on_click(...)`
   described a handler that no view could ever deliver to. `wants_view` now
   asks `gestures::has_gestures` too.

2. **A gesture's sender was a different KIND of thing from every other
   sender.** `fire_click(n)` passed `n as *u8` — the NODE — while a control's
   action passes the native control, and `component::key_of(sender)` is
   written against the latter. One reader, two meanings. `gestures::fire`
   now passes `gesture_sender(n)`: the backing view once mounted, the node
   only when there is no backend to read it anyway.

3. **`item_of` was declared against a verb that did not exist.**
   `SenderReaders.item_of` is documented as "the per-node app pointer set by
   `.item(p)`" and facet had no `.item`, so the row could only ever answer
   null however a backend implemented it. `core::set_item` / `core::item_of`
   now exist. It rides `C_HANDLERS` rather than a bit of its own — the
   shared band is FULL at bits 48..63, and an item is the payload half of a
   handler, so that is the honest place for it.

4. **`keyCode` is an `unsigned short` and the last two arguments are on the
   STACK.** Reading it as u64 picked up the wrong slot. The modifier flags
   ride a register and were always right, which is exactly why this stayed
   invisible until the code was asserted against a synthesized NSEvent.
   Apple's arm64 ABI packs stack arguments at natural alignment; the extern
   has to say `i8` then `u16`.

One design rule worth not re-deriving: **the runtime subclass is SHARED by
every view of its backing kind**, so a per-view capability can never be a
method. Adding `performDragOperation:` for one drop zone would answer for
every node of that kind. Drop selectors go on the class unconditionally and
`registerForDraggedTypes:` — AppKit's own gate — is what a view opts in with.

### Open — decide before the code that depends on them

0. **RESOLVED 2026-08-04 by the user.** `web`/`hybrid_web`: waiting on
   `vendor/webkit`, which the user has in progress (was "skip"; the package
   is being built, so these become implementable rather than deferred). `date_picker`/
   `time_picker`: an extension IS the answer — done, see below.
   `tabs`: implement it, no decision needed — done, NSTabView with a
   TabViewItem per pane.

   The date bridge, for the record: facet's `Date` is a CIVIL date, so the
   backend uses the proleptic Gregorian calendar (days-from-civil, exact and
   locale-free) and PINS the picker to UTC. Pinning is the load-bearing half
   — a civil date has no time zone, so rendered in the machine's local zone
   `2026-01-01` would come back `2025-12-31` anywhere west of Greenwich, and
   the value would not survive its own round trip.

1. **Live structural mutation has no route to the backend.** `set_content`
   and `switch_to` are covered. A bare `(*node).add_child(...)` /
   `remove_child` on a MOUNTED tree — which is how a non-reactive framework
   fills a list — creates a flex node with no native view, and nothing ever
   mounts it: `sync_walk` applies only to nodes that have a dirty word AND
   a view. The old facet had explicit `add_child` / `remove_child` /
   `insert_child` / `replace_child` / `set_child` backend registrars; the
   new seam has none. Three ways out:
   (a) facet grows a structural verb pair that mounts and unmounts through
       the Renderer,
   (b) the sync walk learns to mount attached-but-unbacked children,
   (c) `set_content` / `switch_to` are declared the only structural doors
       and the bare flex verbs are documented as description-time only.
   This changes the seam, so it is the first architectural fork of the
   stage. iris depends on the answer.

2. **The backend has no door to record the native window.**
   `app::Window.native` is declared and never written — no setter, no
   getter, and the field is unreachable from outside `application.cplus`.
   `vocab::WindowRef` has `none()` and `is_open()` but no constructor from
   a raw pointer (`_w` is private), so `core::set_window(n, w)` cannot be
   given a real window either. Both slots exist for the backend and neither
   is reachable. Proposed: `app::set_window_native(root, p)` /
   `app::window_native(root)` and `vocab::WindowRef::of(p)` — but
   `application.cplus` is hand-written under the statics rule, so the shape
   wants confirming rather than assuming.

3. **facet's own test gate becomes coupled to facet_appkit.**
   `test_main.cplus` imports `./runtime`, and on macOS that resolves to
   `runtime_macos.cplus`, which imports the backend. The moment that file
   exists, `cd vendor/facet && cpc test` compiles facet_appkit — a broken
   backend turns facet's 436 red. `facet.old/Cplus.toml` had exactly this
   (`[macos.dependencies] facet_appkit = "*"`), so it is precedent rather
   than a surprise, but it is worth saying out loud before it happens.

4. **facet_appkit's own test posture.** The old package ran real windows
   in-process under `cpc test` with `leaks --atExit` as the harness.
   Assumption unless told otherwise: mirror that. The standing rules that
   bound it are "test our bindings, not Apple's behaviour" and "an agent
   cannot assert drag feel — end feel items with run it and try".

### Facts worth not re-deriving

- **Kind ids**: `props::K_*` 1–38 for the generated controls, `K_NODE` = 0
  for a bare container, and the hand-written four at 1000 `symbol`,
  1001 `tree`, 1002 `split`, 1003 `window_buttons`.
- **Reading a control's props from the backend**: `core::node_data(n)` then
  `{ (*d).props } as *props::XProps`. The generated cursors' `_props()` is
  private (leading underscore), but the `props::XProps` structs and their
  fields are not, so the backend reads them directly — check
  `{ (*d).kind }` first, exactly as the cursors do.
- **View ownership**: `Renderer.create` returns the view and mount pairs it
  with `Renderer.view_release` on the node (M1), so `create` hands back a
  +1 and `view_release` is its release. Node teardown fires it.
- **Who lays out**: nothing in facet calls `calculate_layout` except the
  app-facing `measure()` and the tests. The Renderer has no geometry verb
  by design — the backend owns the layout pass and the frame walk, reading
  `frame()` off flex. Two consequences for the walk: origins accumulate
  across viewless pass-through nodes (a node whose `create` returned 0 has
  no view, so its children hang from the nearest backed ancestor), and the
  Y axis flips unless the host view is flipped.
- **`Chrome`** is `bar: Bar` + `close_button_only`, not the old six
  booleans; `Bar` is `Native | Blended | Hidden | Custom`.
