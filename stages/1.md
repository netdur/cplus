# Stage 1 — re-truth the MAP

Bootstrap of `vendor/facet`, judged against INTENT.md. facet is an empty
package: it has no verbs and no backend. Stage 1 decides, for every row of
MAUI's portable surface, whether facet declares it or not.

Instrument: `tools/maui_map.py`. Input: `plans/facet/spec/maui-spec.json`
(produced by `tools/maui_spec.py` from MAUI's netstandard PublicAPI).
Output: `plans/facet/maui-map-draft.md`.

## The rule

Every row lands in exactly **one of two buckets**:

- **ADOPT** — facet declares it, under a facet name (naming_guideline.md).
- **DROP** — MAUI's model, not facet's. Three reasons, never any other:
  - **MODEL** — MVVM, binding, templates, identity. facet describes UI with
    components, keys, and fn-ptr handlers.
  - **LAYOUT** — layout is flex_layout's. facet Nodes carry flex modifiers.
  - **ENGINE** — MAUI's own internals. Not application vocabulary in any
    framework.

There is no FUTURE bucket, no UNSUPPORTED bucket, and no KEEP-FACET bucket.

- **No FUTURE.** Parking is not a status. A row the rules cannot decide makes
  the script exit non-zero and print the row by name.
- **No UNSUPPORTED.** What a backend cannot do is facet_appkit's sentence to
  pass, against a contract facet has already written. A platform's limits do
  not shape the portable vocabulary. The backend may ignore a word, or
  implement it despite AppKit lacking a direct API — that is a backend
  implementation detail, outside facet's scope.
- **No KEEP-FACET.** facet is empty; there is nothing to keep.

The previous map ran the other way: the backend's capability decided what
facet declared. INTENT reverses the direction of authority, and that
inversion is what Stage 1 implements.

## Result

```
865 rows — ADOPT 486, DROP 379
  DROP 239  MAUI engine internals
  DROP  85  MAUI's MVVM model
  DROP  55  layout — flex_layout's
```

- The 486 ADOPT rows collapse to **338 distinct facet verbs**; the shared ones
  are declared once on `Node` (`set_font_size` covers 7 widgets,
  `set_text_color` 7, `on_submit` 3).
- **Zero verb collisions** — no facet name is declared with two different
  types. The contract is emittable as written.
- **Zero undecided rows** and **zero unclassified types**, both enforced by a
  guard that exits non-zero and names what it found.
- The contract references **58 facet types**, of which these must be declared
  by facet and do not yet exist: `Node`, `Color`, `Brush`, `Shadow`, `Shape`,
  `Spans`, `Corners`, `Insets`, `Rect`, `Size`, `Point`, `Date`, `Duration`,
  `Window`, `Drawable`, `SwipeItem`, `ToolbarItem`, `MenuBarItem`,
  `KeyboardAccelerator`, plus 30 enums (`TextAlign`, `FontStyle`, `LineBreak`,
  `ReturnKey`, `ScrollBars`, `ScrollAxis`, `ImageFit`, `Keyboard`,
  `SelectionMode`, `TextTransform`, `TextDecoration`, `TextType`,
  `FlowDirection`, `ClearButton`, `AutoSize`, `ItemSizing`, `ScrollAnchor`,
  `TableStyle`, `SeparatorVisibility`, `ContentLayout`, `Buttons`,
  `SwipeDirection`, `LineCap`, `LineJoin`, `SafeArea`, `Appearance`,
  `DotShape`, `KeyModifiers`, `ToolbarPlacement`).

Before the type list was closed, the same map read 536 rows — ADOPT 312 /
DROP 224 over 222 verbs. The 329 new rows are the 20 types that were absent
from the extractor, not a change of policy.

For reference, the map as inherited: ADOPT 4, DROP 171, FUTURE 234,
KEEP-FACET 92, UNSUPPORTED 35. The 92 KEEP-FACET rows asserted verbs that no
longer existed ("shipped 0b813b7", "wired in v1"); the 35 UNSUPPORTED rows
deleted words from the vocabulary because NSSwitch and NSButton have no tint
API. Both classes re-entered ADOPT, which is where the growth from 4 to 312
comes from.

## Decisions

1. **facet declares, the backend answers.** 35 rows the old map deleted for
   AppKit's sake are now in the contract — `Switch.OnColor`/`OffColor`/
   `ThumbColor`, `ProgressBar.ProgressColor`, `CheckBox.Color`,
   `Button.TextColor`. facet_appkit will say it cannot, or implement them
   another way; neither answer belongs in facet.

2. **A third DROP reason was unavoidable: ENGINE.** 118 rows, of which 122 of
   the original 130 method-band rows: `MapText`, `SendClicked`, `OnMeasure`,
   `ArrangeOverride`, `BatchBegin`, `OnBindingContextChanged`. Not MVVM, not
   layout, and not application vocabulary in any framework. The methods band
   therefore inverts: whitelist what is vocabulary, drop the rest.

3. **MAUI enums are vocabulary, not drops.** 26 of the 76 value types are
   enums; each becomes a facet enum under a facet name (`TextAlignment` →
   `TextAlign`, `Aspect` → `ImageFit`, `LineBreakMode` → `LineBreak`,
   `ReturnType` → `ReturnKey`).

4. **The transform band adopts.** `Rotation`, `Scale`, `TranslationX/Y`,
   `AnchorX/Y`, `ZIndex`, `Shadow`, `Clip`. The old map parked all of it as
   "no facet transform story yet"; with no parking bucket, it is either
   vocabulary or MAUI's model, and it is vocabulary.

5. **11 `object`-typed rows are Nodes, not bindings.** `ListView.Header`/
   `Footer`, `RadioButton.Content`, `ItemsView.EmptyView`, `Window.Page` →
   `set_root`. MAUI types them `object` only because it binds them. The other
   17 `object` rows are `*CommandParameter` and drop as MODEL.

6. **Six capabilities promoted to shared `Node` methods.** MAUI repeats a
   member on every control that overrides it (`OnBindingContextChanged` x8,
   `UpdateFormsText` x7, `OnMeasure` x7, `ChangeVisualState` x6, `MapText`
   x5); facet has one method on Node, so those repetitions collapse rather
   than multiply. Collapsing is not promoting — a binding-context hook is
   still a hook however many types declare it. What promotes is a capability
   no adopted row already carries:

   | MAUI | facet | why it is not engine |
   |---|---|---|
   | `InvalidateMeasure` | `relayout()` | "this node changed, lay it out again" — the core verb of a keyed-direct framework |
   | `Measure` | `measure(width:height:)` | a size query, not the arrange pass |
   | `BatchBegin`/`BatchCommit` | `begin_updates()`/`end_updates()` | coalesce N mutations into one layout pass |
   | `GetChildElements` | `children()` | tree navigation on a Node |
   | `Handler` | `native()` | the escape hatch INTENT blesses — free to drop beneath facet at will |

   `native()` is the one row in the contract that is deliberately
   platform-specific. facet declares the seam; what the pointer *is* belongs
   to the backend.

7. **23 rows were dropped for the wrong reason.** `Arrange`, `Layout`,
   `LayoutChildren`, `OnMeasure`, `CrossPlatformMeasure`,
   `ComputeConstraintForView`, plus the `Frame`/`DesiredSize`/`DisableLayout`
   properties. Same verdict, honest reason: flex_layout's, not MAUI's
   internals. LAYOUT went 15 → 38.

8. **Chrome owns the window rows, split by band.** facet's window story is
   `Chrome` — declarative presentation metadata a Screen hands the host, not
   a live object an app mutates. You *describe* a window at build time and
   *read* or *observe* it at runtime, so the band decides the owner:
   - 14 writes → **Chrome** (`title`, `width`/`height`, min/max floors,
     `is_maximizable`, `title_bar`, `x`/`y`)
   - 1 write → **Screen** (`Page` → `set_root`; the root subtree comes from
     `Screen::build`)
   - 15 reads/events → **runtime** (`display_density()`, `is_activated()`,
     `observe_window_active`/`inactive`, the modal-stack events)

   This also settles `VisualElement.Window` (read), which stays dropped for a
   stated reason: Chrome is per-Screen metadata and the live window is
   addressed through runtime verbs, so an element has no window to hand back.
   It becomes vocabulary only if facet grows multi-window.

9. **`Cancellable` is not declared; `events::Subscription` is used.** The
   `events` package already carries the RAII contract — `cancel()` idempotent,
   `active()`, `pause()`, `resume()`, `detach()`, and `drop()` unsubscribes.
   Old facet's `Cancellable` was a strict subset written for the same stated
   reason. facet will not ship a second cancel handle. Every `observe_*` row
   declares `events::Subscription`. The `events` package may be edited to
   match facet's needs (its bus payload is `str` today; the typed
   `Signal[T]`/`SignalSubscription[T]` half exists beside it).

10. **Ten name corrections after reading all rows.** `Bounds` restored as a
    read (only `Frame`/`DesiredSize` are the layout system writing back);
    `HeaderElement`/`FooterElement` dropped as the realized half of a bound
    pair; `TableView.Root` → `set_content`, to stop colliding with
    `Window.Page` → `set_root`; corner radius unified on `Corners` across
    Button/RadioButton/BoxView (MAUI types two of them `int`); `IsLoaded` →
    `is_attached()`; `Focused`/`Unfocused` → `on_focus`/`on_blur`, pairing
    with the `focus()`/`blur()` verbs; `Window.SizeChanged` →
    `observe_window_size`; `Opened`/`Closed` reclassified as discrete (`on_`,
    not `observe_`); `uint` → `i64`; `NotifyRowTapped` dropped as engine.

11. **The type list is closed, and a fourth outcome was needed to close it
    honestly.** ALIAS: `Frame` → `Border`, `SolidColorBrush` → `Brush`,
    `AutomationProperties` → `SemanticProperties`, the whole `ImageSource`
    family → `str`. These are not drops — nothing is being refused, it is the
    same surface under another name. Calling them DROP would have been
    dishonest and FUTURE is banned, so ALIAS is recorded as its own outcome,
    with what covers each.

12. **"Not this pass" is not a reason, so every real control went in.** The
    proposal was 17 types; the closure pulled in 20, because a type that is
    genuinely a control cannot be parked. Beyond the 17: `GraphicsView`,
    `HybridWebView`, `ToolbarItem`, `SwipeItem`, `MenuFlyout`,
    `MenuFlyoutItem`. `ToolbarItem` in particular was being swallowed by a
    `Toolbar\w+` engine rule that was too broad — `Page.ToolbarItems` is
    ordinary vocabulary.

13. **The closure check found two capabilities nobody had named.**
    `ToolTipProperties` (a tooltip on any element) and `KeyboardAccelerator`
    (a keyboard shortcut on a command). Neither was in any proposal; both are
    real vocabulary that would have been absent from facet without ever being
    refused. That is precisely the class of hole the check exists to catch.

14. **`Window` becomes a facet type, correcting decision 8's sub-note.**
    `Application.Windows` is a live list of windows, and under the rule that
    is vocabulary — there is no bucket for "facet is single-window today."
    So facet declares a `Window` handle, `windows() -> Window[]` adopts, and
    `VisualElement.Window` promotes to `window()` rather than staying dropped.
    Decision 8 stands for the rest: Chrome still owns the 14 build-time
    writes, because describing a window and holding a handle to one are
    different things.

15. **Three collisions the new types introduced, all resolved.**
    `ImageButton.CornerRadius` joined Button/RadioButton on `Corners` (MAUI
    types it `int`). `Threshold` was two unrelated distances under one name —
    the recognizer's became `set_swipe_threshold`, the view's
    `set_reveal_threshold`, both `f64`. And `children()` now has one type
    everywhere: `GetChildElements` moved out of the method whitelist so it
    agrees with `ScrollView.Children`.

## Closed — the spec's type list

*The section below records the hole as it was found. It is now fixed; the
remaining-work items are done and the numbers above supersede the ones here.*

The rows are all bucketed. The **type list they come from is not**.

`tools/maui_spec.py` extracts 39 types (22 controls, 9 shared bases, 7
recognizers, Window) from three hand-written dicts. **49 other MAUI types
have 3+ settable properties and were never extracted** — so they are neither
ADOPT nor DROP, they are absent. That is more silent than a FUTURE row.

It is already load-bearing, not theoretical. Three types the contract *names*
were never extracted:

- `Label.FormattedText` is ADOPT with type **`Spans`** — `Span` (12
  properties) never extracted.
- `Window.TitleBar` is ADOPT — **`TitleBar`** (7 writes, 2 reads) never
  extracted.
- `VisualElement.Shadow` is ADOPT — **`Shadow`** (4 properties) never
  extracted.

And **`ScrollView` is missing entirely** (8 writes / 4 reads / 2 events / 18
methods). facet currently cannot describe a scrolling view.

The structural cause: the rows are self-enforcing (the script fails on an
undecided row, which is why there is no bucket to hide in), but the type list
had no such check. A hand-written list at the top of a pipeline that is
rigorous everywhere downstream is where the hole was.

### How it was closed — DONE

**356 types** in the manifest carry surface. Every one now lands in one of
four outcomes, checked by `maui_spec.check_type_closure()`, which exits
non-zero and names anything unclassified:

- **EXTRACT — 59 types.** 37 controls, 9 shared bases, 7 recognizers, 6
  runtime types, 5 value types. Spec grew 536 → 865 rows.
- **ALIAS — 24 types.** The same surface under another name; see decision 11.
- **DROP — 273 types**, by family, each with one of the three reasons. The
  families are regexes, not a hand-list, so they hold as MAUI grows: the
  Shell/navigation model, the cell model, binding/template/style machinery,
  XAML markup converters and attributes (MODEL); layout containers and the
  geometry that positions them (LAYOUT); `I*Controller`/`I*Element`
  interfaces, `*EventArgs` payloads, statics and handlers (ENGINE).

The guard is verified, not just written: removing `ScrollView` from the
extract list makes `maui_spec.py` exit 1 naming `ScrollView (32 surface
rows)`. Both halves of the pipeline now fail loudly rather than silently
omitting — the rows since the start of this stage, the types since its close.

`Insets` is no longer dead: `CarouselView.PeekAreaInsets` uses it.

Still true: `tools/gen_contract.py` does not run — it reads `UNSUPPORTED` /
`KEEP-FACET` statuses that no longer exist. That is Stage 2's rewrite; it
should not be invoked meanwhile.

## Stage 1 is complete

Every row of MAUI's portable surface is ADOPT or DROP. Every type in the
manifest is extracted, aliased, or dropped by family. Both are machine-checked
and both fail the build rather than parking anything. The contract facet must
declare is 338 verbs over 58 types, with zero name collisions.
